1. Executive Summary & Problem Statement

In fast-paced enterprise environments, IT support requests frequently become bottlenecked or lost when managed across unstructured communication channels such as email and instant messaging. Common organizational failure modes include:

  • Lack of Centralized Visibility: No single pane of glass for tracking incident volume, severity distribution, or resolution bottlenecks.
  • Absence of Role-Based Governance: Employees either lack visibility into resolution timelines or possess unintended permissions to alter ticket assignments or close incidents.
  • Zero Audit Accountability: Ticket modifications occur without immutable change logs, obscuring who made changes and when.
  • State Loss on Restart: Ephemeral prototype implementations rely on memory or client localStorage, resulting in data loss across server cycles.

HelpDesk 360 resolves these challenges by delivering an enterprise-grade full-stack IT service desk platform engineered with strict role-based access control (RBAC), multi-engine database persistence (SQLite + PostgreSQL), live operational metrics, and complete lifecycle auditability.

2. Solution Overview

HelpDesk 360 delivers tailored workflows for distinct organizational stakeholders:

  • Employee Workspace: Submits structured incidents with client- and server-enforced validation, tracks submitted tickets in real-time, inspects assigned technicians, and reviews full status progression histories. Employees are strictly isolated to their own tickets.
  • Technician Queue: Central queue sorted by operational urgency (urgent → high → medium → low). Technicians can filter by category/status/priority, search by title or ticket ID, reassign tickets to valid technicians, and transition lifecycle states.
  • Operations Intelligence Dashboard: Derives live real-time metrics directly from database queries (Open Issues, Urgent Requests, Assigned Tickets, Completed Work) with breakdown graphs for categories and priorities.
  • Immutable Audit History: Every lifecycle transition writes an immutable audit record containing ticket ID, old status, new status, actor ID, and UTC timestamp.

5. Business Logic & Operational Governance

5.1. Ticket Submission & ID Generation

  • Input Requirements: Title (required, ≤ 200 chars), Description (required, ≤ 3000 chars), Category (one of 4 valid values), Priority (one of 4 valid values).
  • Initial State: Newly created tickets initialize to status open and assigned_to = NULL (Unassigned).
  • Sequential Monotonic IDs: IDs are generated dynamically by inspecting the highest numerical suffix matching HD-<N>, ensuring deterministic sequence progression without collision.

5.2. Priority Ordering & Queue Sorting

Technicians always view unresolved urgent issues at the top of their queue. The SQL sorting query applies an explicit priority weight:

ORDER BY CASE priority
    WHEN 'urgent' THEN 1
    WHEN 'high'   THEN 2
    WHEN 'medium' THEN 3
    WHEN 'low'    THEN 4
    ELSE 5
END ASC, created_at DESC

5.3. Role Restrictions & Data Isolation

  • Employee Isolation: Employees can query tickets via GET /api/tickets, but queries are automatically scoped to WHERE reported_by = current_user.id. Direct requests for other users' tickets via GET /api/tickets/{id} are intercepted and rejected with HTTP 403 Forbidden.
  • Technician Operations: Only technicians can invoke PATCH /api/tickets/{id}/assign or PATCH /api/tickets/{id}/status. Attempting to assign an employee as a technician returns HTTP 400 Bad Request.

8. Production Deployment & Infrastructure Readiness

HelpDesk 360 is packaged for automated cloud deployment via Render.com with multi-region database durability:

  • Cloud Repository: https://github.com/Rithika-SD/helpdesk360
  • Deployment Descriptor: render.yaml automatically provisions a Web Service and a managed PostgreSQL database instance.
  • Unified Build Process: build.sh automatically installs Python dependencies, compiles the React frontend bundle via Vite, and mounts the SPA directly onto Flask's static router.
  • 24/7 Cloud Uptime: When deployed on Render, the service and database run independently of the local workstation, remaining accessible at all times.
